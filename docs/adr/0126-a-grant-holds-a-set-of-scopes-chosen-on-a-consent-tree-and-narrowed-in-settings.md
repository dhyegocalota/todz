# 0126. A grant holds a set of scopes chosen on a consent tree and narrowed in Settings

- Status: Accepted (the loop's call)
- Date: 2026-11-27
- Deciders: Claude (the build loop's call, under the owner's order on 2026-11-27: authorize every project, one, several, whole workspaces or the whole account, "bem dinâmico")
- Inspired by: [0109](0109-mcp-clients-connect-with-oauth-2-1-pkce-and-dynamic-registration-and-a-grant-is-never-more-than-the-equivalent-key.md), [0115](0115-one-oauth-connection-with-the-account-scope-exposes-everything-the-app-can-do-and-task-tools-take-an-explicit-project.md), [0116](0116-an-oauth-decision-answers-a-page-that-returns-to-the-client-and-a-replayed-approval-is-told-so.md), [0125](0125-a-refresh-token-stays-honoured-until-a-token-issued-from-it-or-a-sibling-is-used-and-every-grant-deletion-logs-its-reason.md)

The loop's call: a grant holds a set of scopes in `oauth_grant_scopes` (migration 0022): one `account` row, or any number of `workspace` and `project` rows, each naming exactly the column of its kind, unique per grant and target. The account is an explicit row, never the absence of rows, and an `AFTER DELETE` trigger deletes a grant that loses its last scope, so a project or workspace deletion can never widen a grant to the account. The migration turns every grant's `project_id` into a project row and every grant without one into an account row, and does the same for the live codes, whose new `scopes` column holds the chosen set as JSON. Nothing reads `oauth_grants.project_id` or `oauth_codes.project_id` afterwards; the columns stay unused, because SQLite cannot drop a foreign-key column without rebuilding the table, and rebuilding `oauth_grants` would cascade-delete every token. A grant with exactly one project scope behaves as ADR 0109 and 0115 describe, with its token scope `project:<id>`, and the account is the owner scope as before, answering `owner`. Any other set is a selection: the owner server serves its task tools and a `workspaces` tool that lists only what the set covers, each task tool takes the required `project`, and a project is covered when it is listed or its workspace is, and it belongs to the grant's owner; a project outside the set answers exactly like an unknown one, `move` needs both ends covered and keeps ADR 0115's same-workspace rule, the owner tools are not offered, the MCP limiter keys on the grant as for a project, and fair use, the write budget, suspension and the cloud cap stay per owner. A selection's token scope is its words, `workspace:<id>` then `project:<id>`, sorted. The consent page is a tree of plain checkboxes posting a repeated `choice` of `owner`, `workspace:<id>` or `project:<id>`; the server refuses the account mixed with anything else, an empty choice and any id that is not the signed-in owner's, and folds a project of a ticked workspace into the workspace, so a ticked workspace means its future projects too. A hashed page script, never inline handlers or `unsafe-inline`, adds select-all, expanding, collapsing and the live summary, and the page names what the same client name already holds for the signed-in owner, never a task count. Settings › Connected apps lists the scopes with their live names and `PATCH /owner/connected-apps/{id}` only narrows (`scope_not_narrower` answers 422), inserting the new scopes before deleting the others so the trigger never fires on a half-done change. A project or workspace deletion logs `cascade` only for the grants that lose their last scope. This amends ADR 0109 §6 and §10 and ADR 0115.
