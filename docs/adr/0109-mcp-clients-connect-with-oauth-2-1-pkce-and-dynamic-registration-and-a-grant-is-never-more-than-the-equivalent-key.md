# 0109. MCP clients connect with OAuth 2.1, PKCE and dynamic registration, and a grant is never more than the equivalent key

- Status: Accepted
- Date: 2026-11-26
- Deciders: Dhyego Calota (owner); Claude (advisor). The loop's call under the owner's standing instruction to decide every call, and the owner's order of 2026-11-27 ("quero MCP por OAuth").
- Inspired by: the [MCP authorization specification, revision 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); RFC 9728, RFC 8414, RFC 7591, RFC 7636, RFC 7009, RFC 8707, RFC 8252, RFC 9207 and the OAuth 2.1 draft; [ADR 0014](0014-credentials-are-stored-as-sha-256-digests.md), [ADR 0017](0017-a-2025-era-client-is-named-by-a-session-in-the-directory.md), [ADR 0040](0040-the-owner-signs-in-with-an-email-link-bound-to-the-mac-that-asked-for-it.md), [ADR 0051](0051-the-admin-signs-in-by-a-mail-link-bound-to-the-browser-that-asked-into-a-cookie-session.md), [ADR 0099](0099-the-todz-cloud-admits-at-most-fifty-active-accounts-and-a-monthly-budget-guard-stops-heavy-writes-before-any-included-quota-runs-out.md), [ADR 0101](0101-an-owner-key-is-a-separate-off-by-default-scope-for-the-account-and-project-keys-never-gain-account-powers.md)

## Context

Connecting an agent today means creating a project key in the app and pasting it into the client's configuration, where it lives in a file. Claude Code, Claude.ai connectors, Codex and Cursor can instead add a URL and sign in through the browser, following the MCP authorization specification. The owner wants that, with a consent screen that names the app and lets the owner pick one project or the whole account, revocation in Settings, and every limit of today still applying. The server is a Worker with D1 and no signing secret; the owner already signs in with a magic link.

## Decision

1. **One origin is both the protected resource and the authorization server.** The resource is `<PUBLIC_ORIGIN>/mcp` and the issuer is `PUBLIC_ORIGIN` (`https://api.todz.app` on the cloud, the server's own origin when self-hosted); every URL is derived from it. Without a valid `PUBLIC_ORIGIN` the OAuth routes answer 404 and `/mcp` keeps its plain `Bearer` challenge.
2. **Discovery.** `/.well-known/oauth-protected-resource/mcp` serves RFC 9728 metadata (`resource`, `authorization_servers`, `scopes_supported` `["project","owner"]`, `bearer_methods_supported` `["header"]`, `resource_name`). The root `/.well-known/oauth-protected-resource` is not served: RFC 9728 §3.3 would make its `resource` the bare origin, which is not the MCP resource. `/.well-known/oauth-authorization-server` serves RFC 8414 metadata: the four endpoints, `code` only, `authorization_code` and `refresh_token`, `S256` only, `none` client authentication, the two scopes, and `authorization_response_iss_parameter_supported: true`. Every 401 from `/mcp` carries `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp"`, plus `error="invalid_token"` when a credential was sent. The challenge names no `scope`: the consent screen, not the client, picks it.
3. **Dynamic client registration only.** `POST /oauth/register` (RFC 7591) registers public clients: `token_endpoint_auth_method` absent or `none`, grant and response types inside what the server supports, one to five `redirect_uris` of at most 512 characters that are each `https` on a plain host name (letters, digits, dots and hyphens, or an IP literal) or `http` on a loopback host (`127.0.0.1`, `localhost`, `[::1]`), with no fragment and no user information, and a `client_name` the history can carry as an agent's name (the core's `agentActor` rule: at most 64 characters, no control characters) with no invisible format characters. Custom URI schemes are refused, as the MCP specification requires. The client id is 32 random bytes. A registration that never got a token is unknown after a day; one whose grants are gone stays known for 30 days after its last token, so a disconnected client can connect again; the nightly run deletes the rest. Registration has a limiter per client address, a limiter shared by every client, and no Turnstile, since it is a machine call. Client ID Metadata Documents are not offered: the Worker would fetch URLs a stranger names, and every client we target falls back to registration.
4. **Authorize validates the client before anything can redirect.** `GET /oauth/authorize` first finds the client and matches `redirect_uri` byte for byte against a registered one, except that a loopback URI may change its port (RFC 8252 §7.3). Until both pass, and while any parameter repeats or `state` is over 1,024 characters, every problem renders an error page and nothing redirects, so the endpoint is never an open redirect. After that, `response_type` other than `code`, a missing `code_challenge`, a method other than `S256`, a `resource` other than the MCP resource (RFC 8707) and a scope with no word the server offers redirect back with the RFC 6749 error, the state and `iss`.
5. **Sign-in is the owner's magic link, in the same browser.** With no OAuth browser session, the page asks for the email address behind Turnstile (`request_link`), and the request goes through the app sign-in's limiters and mail budget; a full cloud mails the queue message instead of a link, as today. The answer sets a challenge cookie and mails a link to `/oauth/sign-in#token=…&request=…`. That page reads the fragment, posts the token and the browser's time zone, and the server spends the link only with the challenge cookie, then admits the address through the same path as the app sign-in (the cloud cap, the daily sign-up limit per client and the disposable-address refusal), so a new account is created exactly as today. Spending the link asks no second Turnstile check, unlike the app's: the Turnstile on the email form and the challenge cookie of the asking browser already bind it, and the daily sign-up limit per client still applies. The session is a 30-minute cookie `__Host-todz_oauth` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, so no sibling host can plant one), stored as a digest in `oauth_sessions`, and the challenge cookie is `__Host-todz_oauth_challenge`. Only `/oauth` reads them; they are not an owner API session. One sign-in serves one consent: Approve or Deny deletes the session, so a second app, or a page that tricks a second click, needs a fresh link. The page then returns to `/oauth/authorize` with the same query, built from a fixed path, so the fragment cannot steer it elsewhere. OAuth sign-in needs the email sign-in provider; with the fake one it is unavailable.
6. **Consent names the app and grants one thing.** The screen shows the registered name (escaped), the redirect host, a radio choice of one project of one of the owner's workspaces (the first project is preselected, and a line says a project also lets it move tasks to the other projects of that workspace, as a key does) and, when the client asked for it or asked for nothing, "Your whole account (owner scope)", never preselected, with a warning line. Approve and Deny post back to `/oauth/authorize` with the authorization parameters only (never anything else the query carried), a form token that is the HMAC of the request under the session secret, and must pass the same-origin check of ADR 0051 against `PUBLIC_ORIGIN`. The decision comes from the rendered form alone: an authorize query, a sign-in `request` field or a mailed link that carries `decision`, `choice` or `form_token` is refused before any page renders, and a decision body that repeats one of those fields is refused, so an attacker's link cannot plant a hidden Approve or owner choice ahead of the buttons. The page forbids framing and allows forms only to itself and the redirect URI's origin. Deny redirects with `error=access_denied`. Granted scope never exceeds the requested one; unknown requested scope words are ignored, as RFC 6749 §3.3 allows.
7. **Codes.** 256 random bits, stored as a SHA-256 digest, valid 60 seconds, bound to the client, the redirect URI, the challenge, the chosen scope and the owner. Exchanging spends the row first, so a wrong verifier also burns it. Presenting a spent code marks it replayed and deletes the grant it produced and every token of it; a grant is stored only while its code is not marked, so two exchanges racing each other never leave a working token.
8. **Tokens.** Access and refresh tokens are `todz-at_` and `todz-rt_` followed by 32 random bytes in unpadded base64url, stored only as SHA-256 digests in `oauth_tokens`. The dash keeps them apart from a project key, `todz_` plus random characters, which could otherwise begin with `at_`. Access tokens live one hour and refresh tokens 30 days. Every refresh rotates: it spends the presented refresh token and issues a new pair; access tokens already issued live out their hour (at most ten live per grant), so a refresh in one session leaves another's access token working; that other session's next refresh, past the 30-second leeway, presents a spent token and disconnects the app. Presenting a spent refresh token deletes the whole grant (the family). A grant keeps every unexpired spent refresh token, and one that reaches 1,000 refresh tokens, more than 30 days of hourly refreshes, is deleted instead of forgetting one, so no number of rotations can erase the token a real client will present. A spent token presented again within 30 seconds of being spent is refused without deleting the grant: that is a client retrying or two sessions racing, the reuse interval OAuth providers allow (RFC 9700 §4.14.2). Every token answer carries `Cache-Control: no-store`. A grant's and its client's last use is written when a token is issued, never on an MCP call.
9. **Revocation.** `POST /oauth/revoke` (RFC 7009) takes either token type with the client id and deletes the whole grant when the token belongs to that client; it answers 200 for an unknown token. `GET /owner/connected-apps` lists the owner's grants (id, client name, redirect host, scope, project, created and last used) and `DELETE /owner/connected-apps/:id` deletes one with its tokens; another owner's id answers 404. The Mac app shows them in Settings › Connected apps, next to Account keys.
10. **A grant is the equivalent key, never more.** `project:<id>` resolves to the same `KeyProject` a project key of that project does: its workspace reach, its tools, the per-credential MCP limiter (keyed on the grant), the read throttle, the daily writes and the suspension refusal. `owner` resolves to the same `SessionOwner` an owner key does, with the owner tools only. The token reaches `/mcp` only; `/owner/*` never accepts it. The history names the app by its registered name in both protocol eras, so OAuth needs no MCP session rows. An owner keeps at most 20 grants; a new one evicts the least recently used.
11. **Deletion.** Grants cascade from their owner, project and client, tokens from their grant, so deleting a project or a workspace takes its connected apps with it and never fails on them.
12. **CORS** is only on the metadata documents; the endpoints serve non-browser clients.

## Threat model

| Threat | Control | Residual |
|--------|---------|----------|
| CSRF on consent | `SameSite=Lax` cookie, same-origin check, a form token bound to the session and the request | none found |
| Login CSRF (an attacker's link signs the victim in) | the link spends only with the challenge cookie of the browser that asked | none |
| Open redirect | nothing redirects before the client and the exact redirect URI match; the link page returns to a fixed path | none |
| Code interception | PKCE S256 only, 60-second single-use codes bound to client and redirect URI, replay revokes | none |
| Token leakage | digests at rest, prefixes a scanner matches (and a probe that proves it), header only, `no-store`, short access lifetime, rotation with reuse detection over every unexpired rotation (a grant at 1,000 is revoked), Settings revocation | a stolen refresh token works until the real client refreshes or the owner disconnects the app; a theft that lands within 30 seconds of the real client's refresh is not detected |
| Client impersonation (a stranger registers "Claude Code") | the consent screen shows the redirect host; loopback hosts are labelled as this computer | an owner who approves a lookalike name on a lookalike host grants it, as with any OAuth provider |
| Scope escalation | the grant resolves to the same key objects; granted scope never exceeds requested; owner scope is never preselected | none found |
| Code or markup injection through client metadata | client name and host escaped in every page, length-capped, control and format characters refused; redirect hosts limited to plain names, so the `form-action` source cannot carry a wildcard or a directive | none |
| Login CSRF through a sibling host's cookie | `__Host-` cookies cannot be set from another host | none |
| Clickjacking and double-click lures | `frame-ancestors 'none'`; one consent per sign-in | a lure inside the 30 minutes after the owner signed in, before they decide, can still land one click |
| Registration flood | limiters per address and for all clients, 512-character redirect URIs, a day's life for a registration never used, nightly deletion | bounded rows per day; Claude.ai connectors share Anthropic's addresses, so on a large self-hosted server they share one registration and token budget per address; the limiter shared by every client is one fixed key, so a flood from many addresses can hold new registrations off for everyone for a minute at a time, while connected apps keep working |

## Alternatives considered

| Option | Pros | Cons | Why not |
|--------|------|------|---------|
| Self-contained signed tokens (JWT) | no lookup per call | a signing secret to provision and rotate, no instant revocation | ADR 0014's reason, and Settings must revoke at once |
| Client ID Metadata Documents | the 2026 specification prefers them | the Worker fetches stranger URLs (SSRF, slow hosts) | registration is still allowed and every target client supports it; revisit when one drops it |
| Accept custom URI schemes | some desktop clients use them | the specification forbids them, another app can claim the scheme | a client that needs one keeps using a project key |
| Name the client from `initialize` with MCP session rows | the same as keys | sessions are bound to project keys by a foreign key; a client could rename itself per request | the registered name is the one the owner approved |
| Reuse the app's owner session for the browser | no new table | the cookie would be a full `/owner` credential | a 30-minute `/oauth` session holds far less |

## Consequences

- Migration 0017 adds `oauth_clients`, `oauth_sessions`, `oauth_codes`, `oauth_grants` and `oauth_tokens`; none holds task data.
- Three rate limiter bindings: `OAUTH_LIMITER` for every `/oauth` route and `OAUTH_REGISTER_LIMITER` for registration, both per client address, and `OAUTH_REGISTER_GLOBAL_LIMITER` for registration by every client together, failing closed on a public host like the sign-in limiters.
- Project keys and owner keys work unchanged, except that a 401 for a revoked or unknown key now carries the OAuth challenge, so a client configured with a fixed key header may offer to sign in instead of only failing.
- Cursor registers a `cursor://` redirect address in the versions we know of; it is refused, and Cursor keeps using a project key until it uses a loopback address.

## Evidence

The `oauth-*` unit tests in `apps/api/test/oauth`, the MCP SDK client handshake test, and the Playwright walk `apps/api/e2e/oauth.spec.ts`.

## Revisit when

A client we target requires Client ID Metadata Documents or a custom scheme, the owner wants per-tool scopes, or grants need a lifetime shorter than the refresh token's.
