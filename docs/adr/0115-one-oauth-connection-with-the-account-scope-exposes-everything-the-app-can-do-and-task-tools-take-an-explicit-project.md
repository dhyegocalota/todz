# 0115. One OAuth connection with the account scope exposes everything the app can do, and task tools take an explicit project

- Status: Accepted (the loop's call)
- Date: 2026-11-27
- Amended by: [0126](0126-a-grant-holds-a-set-of-scopes-chosen-on-a-consent-tree-and-narrowed-in-settings.md) (a grant holds a set of scopes, and a selection is served by the owner server without the owner tools)
- Deciders: Claude (the build loop's call, under the owner's order on 2026-11-27 after his connector showed only nine tools: "só tem essas tools?")
- Inspired by: [0109](0109-mcp-clients-connect-with-oauth-2-1-pkce-and-dynamic-registration-and-a-grant-is-never-more-than-the-equivalent-key.md), [0111](0111-api-keys-are-removed-and-an-mcp-client-connects-only-through-oauth.md)

The loop's call: with keys gone, an owner-scope grant is the one connection that must reach everything the app can do, so its server serves the account tools and every task tool of the project server except `projects` (`workspaces` already lists them). Each task tool there takes a required `project` id and no default project exists; every call resolves that project through the directory against the grant's owner (`openOwnedGrantProject`), so a project of another owner answers exactly like an unknown one (`accountNotFound`), and fair use, the daily write budget, suspension and the cloud cap apply per owner as on a project grant. `move` takes the source in `project` and the destination in `destination`, and still reaches only the other projects of the source's workspace. A project-scope grant keeps exactly its narrower set with no `project` argument. Every tool of both servers carries MCP annotations (`title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint: false`) derived from one effect per tool in `mcp-annotations.ts`: reads are read-only and idempotent, adds are neither, a change that only flips a state (done, reopen) is idempotent and not destructive, a change that can overwrite or clear what was there (update, the renames, update_settings) is destructive and idempotent, deletes are destructive and idempotent, and a move is destructive and not idempotent because the task gets a new id. This amends ADR 0109's "a grant is never more than the equivalent key" for the owner scope, which now equals the app's whole owner API.
