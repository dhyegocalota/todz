# 0064. A reply to the day email adds one task, only from the owner's own authenticated address

- Status: Accepted (the build loop's call, the owner may overturn it); extends [0013](0013-a-project-is-reached-only-through-the-directory.md) §2 with a third credential, a reply address whose sender is authenticated
- Date: 2026-11-25
- Deciders: Claude (the build loop's call, pending the owner); Dhyego Calota (owner) asked that "replying adds a task, through Email Routing to a Worker email handler; the reply-to-add part needs its own ADR and security review (only the owner's own address may add)"
- Inspired by: [ADR 0063](0063-the-day-email-is-claimed-once-a-day-per-owner-from-a-quarter-hour-cron.md), [ADR 0014](0014-credentials-are-stored-as-sha-256-digests.md), [ADR 0040](0040-the-owner-signs-in-with-an-email-link-bound-to-the-mac-that-asked-for-it.md) (the mailbox is already the sign-in credential), [ADR 0045](0045-the-public-sign-in-routes-are-limited-three-ways-and-turnstile-guarded-failing-closed.md) (limits), Cloudflare's Email Service documentation read on 2026-11-25 (Email Workers, the `Authentication-Results` header, subaddressing), the zone's Email Routing settings read the same day through `scripts/todz-cloudflare.sh` (enabled, `support_subaddress: false`, rules `hello@` and `support@` forward to the owner, the catch-all disabled), RFC 8601 (`Authentication-Results`), RFC 3834 (`Auto-Submitted`), RFC 3676 (`format=flowed`), the plan and security review of 2026-11-25 (R1–R18 in the feature's `plan.md`)

## Context

Inbound mail is unauthenticated input from the whole internet that would write into a tenant's project. A From header is trivially forged; a reply address can be forwarded or leaked; an old DKIM-signed mail from the owner can be replayed to a new recipient. Email Routing checks SPF, DKIM and DMARC before it invokes a Worker and prepends its own `Authentication-Results` header, but it rejects only mail whose domain's DMARC policy asks for it, and Gmail's policy is `p=none`, so forged Gmail mail still reaches the Worker with `dmarc=fail`. DMARC vouches for a domain, not a mailbox. The owner's mailbox already signs him in (a magic link, ADR 0040), so a reply proven to come from that mailbox grants nothing the mailbox does not already have.

## Decision

1. **A fresh reply address per send.** Each day mail's reply-to is `reply+<secret>@todz.app`, the secret 16 random bytes as 32 lowercase hexadecimal characters (lowercase survives any mail system that folds case). The `day_email_reply_addresses` table keeps its SHA-256 digest, the owner and an expiry 7 days later (ADR 0014); expired rows are deleted on each cron tick, and turning the day email off (`PATCH {day_email: false}`) deletes every reply address of that owner at once. A leaked address dies within a week and adds nothing without the owner's own mailbox.
2. **Routing.** Email Routing's subaddressing is turned on for `todz.app` and one rule sends the literal `reply@todz.app` to the Worker `todz-api`; `reply+<detail>@` falls back to it and the detail is kept in `message.to`. `hello@` and `support@` keep forwarding, and the catch-all stays disabled. The Worker's default export gains `email`.
3. **Every check fails silently, in this order.** A refused message is dropped: no `setReject` (a bounce would confirm the address exists), no reply, no task. One log line records `{event: 'day_email_reply', outcome}` with an outcome enum and never an address, a subject, a header's text or a title; `unauthenticated` adds a verdict enum (which of the rules in 3.7 failed), never the header's `smtp.mailfrom` or `header.from`.
   1. `message.to`, lowercased, matches `reply+<32 hex>@todz.app` → else `unknown_recipient`. No storage is read for any other shape.
   2. The secret's digest names an unexpired row (one indexed read) → else `unknown_recipient`. This yields the owner. There is no global limiter: a stranger's mail never reaches a limiter that a matching secret also counts against, so strangers cannot use up the owner's replies.
   3. A per-owner limiter (5 a minute, keyed by the owner) → `limited`. Cloudflare's rate limiting counts per location, so the bound is per data centre, not global; the daily cap (3.10) is the global bound.
   4. `rawSize` at most 1 MiB → else `too_large`.
   5. The raw message is parsed with `postal-mime`; a parser error → `unparseable`.
   6. An automatic message: `Auto-Submitted` present and not `no`, `X-Autoreply` or `X-Autorespond` present, or `Precedence` in `bulk`, `junk`, `list` or `auto_reply` → `automatic` (vacation responders reply to the day mail).
   7. **Authentication**, read only from `postal-mime`'s raw header list in document order and parsed per RFC 8601 (quoted strings and comments are not results; `ARC-Authentication-Results` is never read): exactly one `Authentication-Results` header names the authentication service, as its exact first token, `mx.cloudflare.net`, and it is the first `Authentication-Results` header of the message; inside it, exactly one `dmarc` result, and it is `pass`, with `header.from` naming the domain D; and at least one `dkim=pass` whose `header.d` is exactly D. A DMARC pass carried by SPF alone is refused: SPF names the envelope, and a shared sending provider's IPs pass SPF for many customers. → else `unauthenticated`.
   8. **The sender**: exactly one `From` header (header names compared case-insensitively after trimming, so `From :` and folded variants count); its value parses to exactly one mailbox, not a group and not two addresses (a comment or display name never counts as an address); that mailbox's domain is D; and its address, normalized like every address (`normalizedAddress`), equals the owner's only `email` identity (an owner with zero or two `email` identities is refused) → else `not_owner`.
   9. **A reply to that mail**: exactly one `To` header, and the same `reply+<secret>@todz.app` address appears in `To` or `Cc` → else `not_a_reply` (an old signed mail of the owner's, replayed to a leaked address, names another recipient in its signed `To`); exactly one `Message-ID` header → else `no_message_id`.
   10. Fewer than 20 replies accepted for this owner in the last 24 hours → else `daily_cap`.
   11. The title (item 4) exists → else `empty`; a title holding a control character (C0, C1 such as U+0085, or a line or paragraph separator) → `invalid_title`.
4. **One task per reply, the title only.** The text part is unwrapped first when it is `format=flowed` (RFC 3676, with `DelSp` honoured). The reply is split into paragraphs (blank-line separated); the quote starts at the first paragraph whose lines, joined, contain `noreply@todz.app` (every client's attribution names the sender, in any language and however it wraps), or at the first line that begins with `>`, is the signature delimiter `-- `, or is Outlook's `-----Original Message-----` or underscore rule. The title is the first non-empty line above the quote, whitespace collapsed and trimmed, cut at `TASK_TITLE_MAX_LENGTH` code points without splitting a character. The rest of the reply is ignored: no notes, no due date parsing, no commands, no attachments. A message with no text part has no title.
5. **Where it lands.** In the Inbox of the owner's first workspace (by creation), due today in the owner's time zone, by the owner (`OWNER_ACTOR`), so it shows in Today at once. Its idempotency key is `mail:` and the SHA-256 of the `Message-ID`, so a redelivered message adds nothing twice. Each accepted reply is recorded in `day_email_replies (owner_id, message_digest, accepted_at)` for the daily cap; rows past 30 days are deleted on each cron tick.
6. **Through the directory.** Only the reply module produces a `ReplyOwner` (a branded owner kept in a `WeakSet`, like `SessionOwner`), and only after checks 3.1 to 3.9; `openReplyInbox` in the routing module looks up that owner's first workspace's Inbox itself and turns it into a stub. An owner with no workspace adds nothing (`no_inbox`).
7. **No confirmation mail.** The task appears in the app through the usual change feed; a refused reply is silent. An unexpected failure (D1 or the project store throwing) rejects the handler with a message that carries no header text; the idempotency key makes any redelivery harmless. Whether Email Routing answers a thrown handler with a temporary SMTP failure (so the sender retries) or records an `Error` and drops the mail is not documented; a spike settles it before the handler is built (plan Step 9), and this item is amended with the answer.
8. **The Email Routing rule is created by the loop** through `scripts/todz-cloudflare.sh api` (its allowlist already admits `/zones/<zone>/…`), after the deploy that ships the `email` handler: subaddressing on, then `POST /zones/<zone>/email/routing/rules` with `{"name": "todz day email replies", "matchers": [{"type": "literal", "field": "to", "value": "reply@todz.app"}], "actions": [{"type": "worker", "value": ["todz-api"]}], "enabled": true}`. The token read the rules on 2026-11-25; whether it may write them is unproven. An authentication error makes both an owner step in the dashboard (Email Routing → Settings → Subaddressing on; Routing rules → Create address `reply`, Send to a Worker, `todz-api`). Deleting the rule turns the feature's inbound half off without a deploy.
9. **No `@todz.app` account or waitlist address.** With subaddressing on, `hello+x@todz.app` forwards to the owner and `reply+x@todz.app` reaches the Worker, so the sign-in link request and the waitlist join refuse any address on `todz.app` with their usual generic answers.

## Alternatives considered

| Option | Pros | Cons | Why not |
|--------|------|------|---------|
| Per-send `reply+secret@` with subaddressing and one rule (chosen) | one rule for every owner; secrets expire; digests only | a zone setting to turn on | — |
| A signed token in the subject or a header, replies to `reply@` | no subaddressing | clients rewrite subjects; a header is not echoed by replies | not carried back reliably |
| An HMAC token in the address, no table | no storage | a Worker secret to manage and rotate; no expiry without more fields | the table is smaller than the secret's runbook |
| A catch-all to the Worker | no zone setting | every typo and spam to any `@todz.app` invokes the Worker | widens the surface |
| One rule per owner | no subaddressing | 200-rule limit; an API write per owner | does not scale |
| From check alone | simple | From is forged freely; Gmail's DMARC is `p=none` | not authentication |
| DMARC pass alone, any alignment | simple | an SPF-only pass vouches for a shared provider's IPs, not the owner | aligned DKIM required |
| A global limiter before everything | bounds Worker work | strangers exhaust it and the owner's real reply is dropped | shape check first, per-owner limit only |
| Bounce refused mail (`setReject`) | the sender learns why | confirms live addresses to an attacker; backscatter | silent drop |
| Several tasks per reply, one per line | faster capture | a quoted line or a signature becomes a task | one per reply, as asked |
| A confirmation mail per add | feedback | a second outbound path and mail volume | the app shows it live |
| The workspace the owner picks | precise | another setting | the first workspace's Inbox until asked |

## Consequences

- A runtime dependency, `postal-mime` (4.2.1, MIT-0, no dependencies, no install scripts), parses inbound MIME in the Worker.
- One rate limiter binding and two tables join the configuration and migration 0008.
- An owner whose mail domain publishes no DMARC record (`dmarc=none`), or whose provider signs DKIM with another domain than his From, cannot add by reply; the mail still arrives.
- A residual risk stays: anyone who can send DKIM-signed mail as the owner's own domain with his exact address (a compromise of his mail provider or his account) can add tasks, which is no more than that mailbox already can by signing in.
- An owner who signs in with a `+tag` address must reply from that exact address; Gmail replies from the bare address, which is refused. The mail's reply hint says to reply from the sign-in address.
- Subaddressing widens `hello@` and `support@` to `hello+anything@` and `support+anything@`, all forwarded to the owner; decision 9 keeps todz's own mails from being sent to them.
- A forwarded day mail lets its reader reply, but the reply is refused unless it comes from the owner's own mailbox and names that address in its `To` or `Cc`.

## Evidence

Cloudflare's Email Workers documentation (2025-07 changelog and the email handler page, read 2026-11-25): "Email Routing validates DMARC before invoking your Worker. It prepends a standard `Authentication-Results` header … read the first `Authentication-Results` header … and verify that its authentication service identifier is `mx.cloudflare.net`. Other `Authentication-Results` headers may have been supplied by the sender and should not be trusted"; with subaddressing on, "`user+detail@example.com` … will be matched by the `user@example.com` routing rule … the `+detail` part … is preserved in `message.to`". The inbound flow rejects only "mail that fails authentication according to the sender's DMARC policy"; the routing statuses include `Handled` and `Error`, and nothing states whether a thrown handler retries. The documented header example is simplified (`spf=pass; dkim=pass; dmarc=pass`), so whether Cloudflare writes `header.from` and `header.d` is unproven until the spike (plan Step 9) captures one real header. `GET /zones/06490974636c535e2cbfd7c5b09925a5/email/routing` answered `enabled: true`, `support_subaddress: false`; the rules listing answered the two forwards and a disabled catch-all. `npm view postal-mime` on 2026-11-25: 4.2.1, modified 2026-11-10, no `dependencies`, no `preinstall`, `install` or `postinstall`.

## Revisit when

The spike shows Cloudflare's header lacks `header.from` or `header.d` (then this ADR is amended before the handler ships), the owner wants several tasks per reply, notes or a due date from the reply, a confirmation, another workspace, or replies from a second address; or Email Routing changes where it puts its verdict.
