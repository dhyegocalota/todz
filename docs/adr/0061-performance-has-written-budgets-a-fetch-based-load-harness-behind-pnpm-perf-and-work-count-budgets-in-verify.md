## Context

todz has never been measured. Every MCP call and owner request crosses up to three remote stores in series: the D1 directory (the key or the session, then the project's ownership, and for a 2025-era client the MCP session), then one Durable Object per project. A task write reads every task of its project to place the new one, and the history and state listings have no index. The app keeps its whole board in memory, rebuilds its task views on every read, and rewrites a project's whole cache file on each change. Nobody knows which of these matters at the owner's scale, because no number exists.

The owner wants budgets, load and stress tests, fixes and a regression check. Production is live with real owners, runs on the Workers Free plan (10 ms of CPU per request, daily request and row caps) and must never be stressed. A dedicated production owner cannot be created by the loop: the only production sign-in is an email link to a real inbox.

## Decision

1. **Budgets.** At the target load (point 2), measured from the client:
   - MCP `tools/call` (`list`, `add`, `done`) and owner API requests: p95 under 150 ms and p99 under 400 ms, with zero 5xx answers. A 2025-era client's `initialize` is measured on its own: p95 under 400 ms.
   - The change feed: from the moment one client sends a write to the moment another client holds the changed task (the socket's `changed`, then `GET …/changes`), p95 under 1,000 ms.
   - Many projects: an owner with 200 projects in 20 workspaces lists them (`GET /owner/workspaces`) within the API budget.
   - The macOS app, signed in with a cache of 5,000 tasks in one project: cold launch (process start to the first task rows on screen) under 1,000 ms as the median of five launches, none over 1,500 ms; a scripted scroll from the first row to the last with no frame over 50 ms and at most 1% of frames over 1.5 times the display's refresh interval; resident footprint after 30 minutes of a steady soak within 10% of its value at 5 minutes; the model work one change costs on the main actor (the board, the task views, the menu bar count and the widget snapshot) under 8 ms, half a 60 Hz frame, as the median a benchmark prints (point 7).
   - The landing on a phone profile (Lighthouse 13.6.0 through `pnpm dlx`, median of three runs, the procedure of ADR 0060): LCP under 2.5 s, CLS under 0.1 and Total Blocking Time under 200 ms, the lab stand-in for INP.
   - Stress, local only: the breaking point, where 5xx answers pass 1% or p99 passes 2 s, is at least four times the target load.
2. **The target load** is 50 requests a second for 2 minutes, the most production may take. The mix: 40% MCP `list`, 20% `add`, 20% `done` (each completing a task the run added), 20% owner API (workspace list, change reads, task writes). The MCP share falls on one project, the hottest Durable Object an agent swarm can make; the owner share spreads over the many-projects owner. Locally the run uses both MCP eras half and half. In production the owner share becomes MCP `list` (point 5) and the run uses only the 2026-07-28 era, so it leaves no MCP session rows in D1.
3. **The harness is a TypeScript workspace package, `tools/perf` (`@todz/perf`), behind `pnpm perf`.** It schedules requests on an open model (each request starts at its planned time, whatever the previous ones did, so a slow server cannot hide its queue), times each HTTP exchange around `fetch`, and computes nearest-rank percentiles itself. MCP calls go through `@modelcontextprotocol/client` 2.4.0, already pinned in the lockfile, with a timing `fetch`, so the requests are the ones real clients send in both eras; owner calls and the change feed use Node's own `fetch` and `WebSocket` (whose `{ headers }` init carries the session; if it cannot, `undici@7.30.2`, already in the lockfile, is pinned in its place). It adds no package the lockfile does not already hold. It prints one row per scenario with the count, the achieved rate, p50, p95, p99, the maximum, the 5xx count and the verdict against point 1, and exits non-zero on a missed budget.
4. **Where it may point.** The target is an enum with two fixed origins, never a free URL: `local` (`http://localhost:8787`, `wrangler dev` with the fake sign-in provider) and `production` (`https://api.todz.app`). Locally, each run signs in a fresh owner through the fake provider and seeds what it needs (a project of 5,000 tasks, the many-projects owner, keys). The stress ramp (from 50 requests a second, times 1.5 every 30 s, until it breaks) runs only on `local`. On `production` the plan refuses any rate over 50 a second, any duration over 120 s, any scenario but MCP, and any run without the key; and the guard lives on the wire, inside the `fetch` handed to the MCP SDK: it throws before sending anything that is not `POST https://api.todz.app/mcp` (an OAuth discovery `GET`, a `GET /mcp` stream, a `DELETE`, another origin), sets `redirect: 'error'`, never retries a 401, keeps at most 50 requests in flight, and one wall-clock timer of 120 s from the first request aborts everything still in flight, cleanup included. Adds stop at 100 s; the last 20 s send only `done`. Sign-in, waitlist and admin routes are never requested, and no limit or Turnstile setting changes.
5. **The `todz-perf` account.** The owner creates a workspace named `todz-perf` in his own production account, issues an MCP key for its Inbox in the app, and stores it in the macOS Keychain under the service `todz-perf-key` with `security add-generic-password -U -s todz-perf-key -a todz -T /usr/bin/security -w`, whose `-T` pre-authorizes the `security` tool so no approval dialog waits. The harness reads it itself with `security find-generic-password -s todz-perf-key -w` under a 5 s timeout, never from an argument, a variable or a file, and never prints it; a failed or timed-out read stops the run before any request. A key reaches only its own project ([ADR 0013](0013-a-project-is-reached-only-through-the-directory.md)), so the run cannot touch the owner's other data. Each run draws an identifier, and every task it adds carries it in its title (`todz-perf <run> #<slot>`) and its idempotency key. The run cleans up after itself within its 2 minutes: it lists the open tasks whose title carries its own identifier and completes those, and only those, so a task the owner put in that Inbox, or another run's, is never touched, and an add whose answer was lost is still found. It ends by reporting the open count of a final filtered list, which must be 0; a separate cleanup-only run, `production --cleanup <run>`, has its own caps (50 a second, 60 s). No route deletes a workspace or a task, so the `todz-perf` workspace and its done tasks stay; the owner revokes the key in the app afterwards. The owner API and the change feed are measured in production only by the production smoke walk (point 7), because the loop holds no owner session there and never will.
6. **Attribution.** The `/mcp` and `/owner` answers carry a `Server-Timing` header with the time spent in the directory and in the project store, so a slow percentile can be split between D1, the Durable Object and the network without a profiler; the harness reports that split per scenario in local and production runs alike. When the MCP handler answers with a stream, the Worker reads it to its end before setting the header and answers the same bytes. CPU time per request comes from `wrangler tail` (`cpuTime`, `outcome`) during a production run, because `wrangler dev` neither reports nor enforces it.
7. **The app is measured by a probe and by model benchmarks.** A probe in the app, off unless the process's arguments (`ProcessInfo.processInfo.arguments`, never `UserDefaults`) hold `-TodzPerfProbe YES`, logs public integers only to the unified log (subsystem the bundle identifier, category `perf`): the launch time, the frame intervals of a scripted scroll, the footprint every 30 s, and the moment each task number of the project the window shows reaches the board from a pull. Without the argument it starts nothing. `pnpm perf app` reads those lines with `log show` and checks them against point 1; joined with a production run's send times, the arrival lines give the change feed's latency in production with the owner's Release app open on `todz-perf`, which is how the production smoke walk re-checks the budgets. A TodzKit benchmark, skipped unless `TODZ_BENCHMARK=1`, prints the model work of point 1 with 5,000 tasks (the median of seven runs after one warm-up); the runbook runs it and records the medians, and nothing asserts them. Launches stay few and short and run in the background with `open -g`, because a window that takes focus disturbs the owner.
8. **The regression check in `pnpm verify` counts work, not milliseconds.** Wall time on a busy laptop is noise; work is deterministic. The API's unit suite gains budget tests that count, for each route kind and MCP era, the D1 round trips (each `first`, `all`, `run`, `raw` or `batch` call, whatever it holds) and, separately, the D1 statements prepared, the Durable Object calls made, and, on a project of 5,000 tasks seeded by one transactional insert, the SQLite rows each use case reads. Each count is asserted at or under a named budget constant, set after this feature's fixes: exact for round trips, statements and Durable Object calls, with a tenth of headroom for rows read, which SQLite's planner may move by a few. A change that adds a round trip or a full scan fails the `unit` gate. The app's budget tests, in the `macos` gate, are deterministic counters as well: how many times the task views are built per read, how many project-file writes happen on the main actor, and how many writes a burst of saves coalesces into.
9. **Fixes follow the numbers.** A candidate is fixed, red-first, when it grows with the size of a project or the number of projects (a full scan or a statement per project on a single-task path), when a single-call path makes two or more directory round trips in series (a local D1 is a file and cannot show what each costs in production, where each is a network hop), when it holds at least a quarter of a missed percentile by attribution, or when it is the first thing to fail in the stress ramp below four times the target. Anything else is recorded as measured and not fixed, with its number.
10. **Numbers live in `docs/runbooks/performance.md`.** The runbook holds every procedure above with its expected result and its `If it fails` line, and a dated results table (date, commit, where, scenario, load, the hot project's done-task count, p50, p95, p99, 5xx, verdict) with a row for each run, before and after each fix; the done count keeps a larger project from passing for a slower server. The build loop runs the runbook's local steps and, under the owner's authorization in `todz-loop/PROMPT.md`, its bounded production step, off-peak and at most once a day: one run is at most 6,000 requests, about 6,000 directory rows read and about 12,000 project-store rows written, well inside the Free plan's daily caps.

## Alternatives considered

| Option | Pros | Cons | Why not |
|--------|------|------|---------|
| `autocannon`, pinned | Mature, fast, prints percentiles | A new dependency tree; closed-loop by default, so a slow server lowers the rate and hides its queue; requests are static or need per-request hooks to chain an `add` to its `done` or to speak the MCP handshake | The scenarios are stateful and MCP-shaped; the hooks would rebuild the harness inside it |
| k6 | Scenario language, open-model executors | A machine install (a Go binary), which the loop may not do; JavaScript in a non-Node runtime, so no MCP SDK | Forbidden install |
| A TypeScript harness with `fetch` and the MCP SDK (chosen) | No new package; real client requests in both eras; open model; percentiles in one tested module | Its own code to maintain and test | — |
| Wall-clock budgets in `pnpm verify` | Closest to the budgets | Flaky on a loaded machine, as the `macos` gate's history shows; a red gate that is noise trains everyone to rerun | Work counts are deterministic and catch the regressions that matter (a new round trip, a full scan) |
| A dedicated production owner made by the loop | A clean account, owner API and change feed measurable in production | Needs a mailbox the loop can read, or the fake provider in production, which [ADR 0020](0020-sign-in-goes-through-a-provider-port-and-v1-ships-only-the-fake.md) keeps to development and tests | Not possible without weakening sign-in ([ADR 0040](0040-the-owner-signs-in-with-an-email-link-bound-to-the-mac-that-asked-for-it.md)) |
| The owner's own session in the Keychain for the loop | Owner API in production | A credential to all of the owner's data in an agent's hands | The MCP key reaches one project only |
| XCTest UI tests with `XCTApplicationLaunchMetric` | Apple's launch metric | A UI test target, a runner that drives the screen during `pnpm verify`, disturbing the owner | The probe measures the same interval in a short, backgrounded walk |

## Consequences

- `pnpm perf` exists with the subcommands the runbook names; `tools/perf` joins `AGENTS.md`'s layout and `scripts/verify-gates.tsv` (`typecheck unit`).
- Every PR that touches `apps/api/src` or `libs/core` can now fail on a work count; raising a budget constant is a reviewed change with its reason in the PR.
- `/mcp` and `/owner` answers gain `Server-Timing`.
- The app gains a probe that costs nothing unless its launch argument is set.
- The production run leaves a `todz-perf` workspace with done tasks titled `todz-perf <run> #<slot>` in the owner's account, and a key the owner revokes by hand.
- The ADR was amended before any code by the plan review of 2026-11-25 (R1 to R23 in `docs/features/performance/plan.md`): the wire guard, the run identifier, the Keychain timeout, round trips counted apart from statements, the round-trip rule of point 9, and counters in place of timings for the app's gate.
- The production smoke walk gains the bounded run and, with the owner's app open, the change feed's production latency.

## Evidence

Read on `main` at `2cbca72` on 2026-11-25:
- `apps/api/src/project-routing.ts`, `directory.ts`: an MCP call reads its key in one D1 statement (a four-table join); a 2025-era call adds a second for the session (`mcp-sessions.ts`); an owner project route reads the session, then the ownership, two statements in series (`owner-endpoint.ts`, `owner-project.ts`), before the Durable Object.
- `libs/core/src/add-tasks.ts` and `update-task.ts` call `listAllTasks`, which reads every open and done task of the project to find one order key.
- `apps/api/src/project-schema.ts`: no index on `tasks (state, order_key)` or `task_history (task_number)`.
- `apps/api/src/mcp-server.ts`: `next` with the nudge on calls the Durable Object twice.
- `apps/macos/TodzKit/Sources/TodzKit/AppModel.swift`: `taskViews` is computed, applying the outbox to the board on every read; `AppModel+Cache.swift`: `keepInProjectFile` reads, decodes and rewrites a project's whole file for one task, on the main actor.
- `apps/api/wrangler.jsonc`: no rate limiter on `/mcp` or `/owner`; the nine limiters guard sign-in, the waitlist and the admin only.

No number exists yet; the first run of the runbook writes the first row.

## Revisit when

- Production misses a latency budget after every fix the decision rule allows; the next candidates are Smart Placement, D1 read replicas or a cache of key lookups, each with its own ADR because each changes where data lives or how fast a revocation lands.
- The plan leaves Workers Free, which changes the CPU limit and the daily caps.
- An owner's project passes 5,000 tasks, or an owner passes 200 projects.
- A route to delete a workspace exists, so the `todz-perf` workspace can be removed after a run.
