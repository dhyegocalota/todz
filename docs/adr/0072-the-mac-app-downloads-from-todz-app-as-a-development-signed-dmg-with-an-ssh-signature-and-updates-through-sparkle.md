# 0072. The Mac app downloads from todz.app as a development-signed DMG with an SSH signature, and updates through Sparkle

- Status: Accepted
- Date: 2026-11-25
- Deciders: Claude (the build loop's call, under the owner's "vamos sem notarizar"); Dhyego Calota (owner) may overturn it
- Inspired by: `todz-loop/PROMPT.md` → `mac-distribution`, the `mac-distribution` spike of 2026-11-25 (below), [ADR 0035](0035-with-the-personal-team-the-widgets-share-the-app-group.md), [ADR 0033](0033-without-a-team-the-widgets-share-a-folder-in-application-support-that-an-app-group-replaces-later.md), [ADR 0049](0049-todz-app-is-served-by-the-same-worker-dispatched-by-host-in-three-features.md)

## Context

The owner wants a public download now, without the Apple Developer Program, "de forma segura e verificada". Without Developer ID there is no notarization, so Gatekeeper rejects every build we can make; what remains is to make each build traceable to a tagged commit, verifiable by anyone, and updatable without a second Gatekeeper prompt.

The machine has one signing identity, an Apple Development certificate of team `XFWR794VS8` (the Personal Team of ADR 0035). `minisign`, `cosign` and `signify` are not installed, and the loop may not install tools. Homebrew's OpenSSL 3.6 is present on this Mac but not on a visitor's: macOS ships LibreSSL 3.3.6, which cannot verify an Ed25519 signature (`unknown option '-rawin'`). macOS ships OpenSSH 10.3, whose `ssh-keygen -Y` signs and verifies Ed25519 signatures over files. The `todz-cloudflare` token cannot use R2 (`wrangler r2 bucket list` → `Authentication error [code: 10000]`), and the owner's session declined an account-wide R2 permission. The token already deploys the Worker, and a Worker's static assets take files up to 25 MiB each; the measured DMG is 4.7 MB.

## Decision

1. **Signing.** The release is the Release configuration signed by Xcode with the team's Apple Development identity. In both targets the Release configuration sets `ENABLE_HARDENED_RUNTIME: YES` and `CODE_SIGN_INJECT_BASE_ENTITLEMENTS: NO`, so no `get-task-allow` ships; Debug keeps the hardened runtime off. The app embeds no provisioning profile, and its entitlements (sandbox, network client, the team-prefixed App Group, Sparkle's two mach-lookup exceptions) need none, so nothing binds it to a registered device. The release script refuses a build unless the app and its widget extension both carry `TeamIdentifier=XFWR794VS8` and the `runtime` flag, pass a strict deep verification, hold no `get-task-allow`, no `com.apple.developer.` entitlement and no `embedded.provisionprofile`, and the built Info.plist names the expected feed and `SUPublicEDKey`.
   **Fallback, not built:** if the owner's check on a Mac outside this one (todz-6f, his other notebook) shows the app killed at launch or the "would like to access data from other apps" prompt for the App Group, a superseding ADR signs the release ad hoc and moves the widgets' shared files to ADR 0033's folder in Application Support for that build.
   **Owner's decision (2026-11-25, relayed by his session todz-6f), not the loop's call:** the owner accepts that the Apple Development identity shows his Apple ID address in every public build's signature. Keep the App Group and the Team ID check. A Developer ID under Logic Bit stays the later upgrade (decision 10). Publish only once the other-notebook check passes.
2. **Package.** A DMG made by `hdiutil` (UDZO, the app and an `Applications` link), itself signed with the same identity, named `Todz-<version>.dmg`.
3. **Sum and detached signature.** `Todz-<version>.dmg.sha256` in `shasum -a 256` format, and `Todz-<version>.dmg.sig`, an SSH signature (`ssh-keygen -Y sign`, Ed25519, namespace `todz-release`, principal `release@todz.app`). The public key is the allowed-signers line in `apps/macos/release/allowed-signers` and on the "Install on Mac" docs page, with its SHA-256 fingerprint (`ssh-keygen -lf`) and Team ID `XFWR794VS8`; it is not served on `todz.app`, the host that serves the binary. The repository is private, so the owner also adds the key as an SSH signing key on his GitHub account, which publishes its fingerprint outside the `todz.app` zone. A visitor verifies with `shasum -a 256 -c` and `ssh-keygen -Y verify`, both on every Mac. The page states the limit plainly: "The signature proves a download is the file the todz release key signed. It does not protect against someone who controls the todz.app zone or todz's Cloudflare account, because this page is served from that zone too."
4. **Keys.** The release key is the base64 of an OpenSSH Ed25519 private key in the login Keychain item `todz-release-key`. The script starts its own agent (`ssh-agent -a ~/.todz-release/agent.<pid>.sock -s`), gives that agent's `SSH_AUTH_SOCK` only to the commands that use it (an inherited one is never used), refuses unless `ssh-add -l` reports no identities, loads the key with `ssh-add -t 120 -`, signs, and kills the agent and removes the socket from a `trap` on exit, interrupt, termination and hang-up. The key touches a file only while `--create-release-key` runs: the file `ssh-keygen` writes inside `~/.todz-release`, deleted before it returns; it reaches the Keychain through `security -i` on standard input unless `security add-generic-password -w` is proven to read standard input. Sparkle's EdDSA key is the one Sparkle's `generate_keys` puts in the login Keychain, read only by `sign_update`. Neither is echoed, logged or passed on a command line, and `.agents/hooks/guard-secrets.sh` refuses an agent command that reads either item, except the release command itself. The item has an empty trusted-application list (`security -i` with `-T ""`), so `/usr/bin/security` is not trusted and every read of it asks the owner (Allow, never Always Allow); a throwaway keychain showed a default item read at once and a `-T ""` item waiting for approval. The keys are protected by the owner's macOS session, not from processes running in it.
5. **Hosting.** The release files are the Worker's own static assets, deployed with the code, so no permission beyond the deploy token's is needed (least privilege). The DMGs never enter git. Every build, dry runs included, goes to `~/.todz-release/builds/<version>/` (mode `700`); only a real release copies its build into `~/.todz-release/site/download/<version>/`, and only after its production checks pass is the version appended to `~/.todz-release/site/released`. Every Worker deploy goes through `scripts/deploy-worker.sh`, which fills a new empty directory with `git archive HEAD apps/api/public` and the latest two versions in `released` (each directory matching the version pattern, each holding only `Todz-<version>.dmg`, `.sha256` and `.sig`, each passing its sum and its signature, each matching production's sum where production serves it), plus the newest released version's signed appcast as `download/appcast.xml`. It refuses a symlink, any other entry, or a foreign `_headers`, `_redirects` or `.assetsignore`, and writes `_redirects` (`/download` and `/download/latest` → `302` to the newest DMG; the `302` carries at least `Location`) and `_headers` (the public folder's rules, then one rule per staged file: `Content-Disposition: attachment` on each DMG, `Cache-Control: public, max-age=31536000, immutable` on every versioned file, five minutes on the appcast). It deploys with `wrangler deploy --assets <that directory> --message <HEAD sha>` through `scripts/todz-cloudflare.sh` and records the new version id. A path that is not a staged file falls to the Worker and answers the site's `404`, so the version guard is the file set itself; the version before the newest stays because Sparkle has no deltas and the appcast is cached for five minutes, so an app holding the previous appcast still finds its DMG, and anything older answers `404`. The staging refuses when production serves a version the release folder lacks, or when a production request fails for any reason but a `404`, so a deploy never removes the published download. A file over 25 MiB stops the staging: the fallback is an R2 bucket behind the Worker, by a superseding ADR.
6. **Updates.** Sparkle `2.10.1`, pinned in `project.yml` by its commit `ab7d71291238df6e0492143b120c9b696a35f603` (the generated project's `Package.resolved` is never committed, so a version range would float), in the app target, with the sandboxed installer service. The appcast holds the latest release; `sign_update` signs both its enclosure and the feed itself, and Release sets `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction`, so Sparkle trusts neither a feed nor an update that does not verify against `SUPublicEDKey`. The feed carries no description and no release-notes link. After the first install every update is trusted without notarization. Checks run daily with Sparkle's gentle reminders: a scheduled check never brings a window over another app; the update waits for the next launch or "Check for Updates…", and the owner confirms each install. Debug has no feed and starts no updater.
7. **Versions.** The version is the one whose `builds/<version>/commit` holds `HEAD`'s hash, else the next patch after the highest `mac-v*` tag (or `--version` when greater); the build number is that commit's `git rev-list --count`, greater than production's appcast `sparkle:version` or equal when that appcast is this version. Both are passed to `xcodebuild`; no release commits to `main`. The tag `mac-v<version>` is created and pushed only after the production checks pass.
8. **Automation.** `pnpm release:mac` (`scripts/release-mac.sh`) does a release end to end, refuses anything but a clean `main` equal to `origin/main`, is idempotent per version, never overwrites a published file, has `--dry-run`, and is tested by `scripts/release-mac.test.sh`. A complete build for `HEAD` is re-checked and reused, never rebuilt. It re-deploys only code the runbook already deployed: it refuses unless the active deployment's message is `HEAD`'s sha, records that version id, deploys through `deploy-worker.sh`, checks production (the `302` of `/download/latest`, the DMG's `200`, its sum, its signature, the appcast's version and signature), and on any failure runs `wrangler rollback <that version id>`, removes `site/download/<version>/` and leaves `released` unchanged. Only then does it append to `released`, tag and push. "Already published" exits 0. Every external tool call runs under a time limit so a Keychain prompt cannot hang an unattended run. Agents deploy only through the repository skill `deploy`: `docs/runbooks/deploy-the-api.md` (whose deploy step is `deploy-worker.sh`), then `pnpm release:mac` when `apps/macos` changed since the highest `mac-v*` tag, then the production checks, stopping at the first failure. Each release is recorded in `docs/runbooks/release-the-mac-app.md`.
9. **Disclosure.** The landing's download button carries one line, "Not notarized by Apple yet: the first time, open it from System Settings › Privacy & Security.", linking the "Install on Mac" page, which also carries the verification steps.
10. **Notarization, switched off.** The script holds `notarize_and_staple` (`xcrun notarytool submit --keychain-profile todz-notary --wait`, `xcrun stapler staple`, then `spctl -a -vv` must answer `accepted`) behind a constant that is `false`. Turning it on is: buy the Developer Program, create a Developer ID Application certificate, switch the signing identity, store the notary profile, flip the constant, supersede decisions 1 and 9.

## Alternatives considered

| Option | Pros | Cons | Why not |
|--------|------|------|---------|
| Apple Development signature, hardened runtime (chosen) | Team ID visible to `codesign -dv`; Sparkle can compare signatures; the App Group of ADR 0035 keeps working | Gatekeeper rejects it; the certificate's name, the owner's Apple ID address, is in every copy's signature | — |
| Ad hoc signature | No certificate at all | No Team ID to verify; the App Group prompts (ADR 0033), so the widgets need the Application Support folder | Kept as the fallback of decision 1 |
| minisign | Small, made for this | Not installed, and visitors would need to install it | The loop may not install tools; verification would need a tool the visitor lacks |
| Sigstore (`cosign`, keyless) | No long-lived key | Not installed; every signature, its artifact hash and the signer's identity go to the public Rekor log; visitors need `cosign` | Same as minisign, and leaks more |
| OpenSSL Ed25519 (`pkeyutl -rawin`) | Plain keys | macOS's LibreSSL 3.3.6 cannot verify it | Fails on a stock Mac |
| GPG detached signature | Familiar | Not on a stock Mac; key management heavier than SSH's | Visitors would need GnuPG |
| SSH signature (`ssh-keygen -Y`, chosen) | On every Mac; Ed25519; namespaced; the same format git uses | Keys need the agent detour to stay off disk | — |
| Worker static assets, staged at deploy (chosen) | No new permission or binding; served with the code; a rollback restores the previous files | 25 MiB per file; every deploy must stage the release folder; the files answer on every host the Worker serves, `api.todz.app` too | — |
| R2 bucket behind the Worker | No size limit that matters; deploys and releases independent | Needs an R2 permission the token lacks (`10000`) and the owner declined account-wide; a binding and a route to guard | The fallback when a DMG passes 25 MiB |
| GitHub Releases | Free hosting | The repository is private, so its release assets are too | Not public |
| GitHub Actions release on tag | Reproducible runner | The signing identity and both private keys as repository secrets; paid macOS minutes on a private repository | Off unless the owner asks |
| Bump the version in a commit | The version visible in `project.yml` | A release would commit on `main`, which the conventions forbid | The tag carries it |
| No updater | Nothing to add | Every fix needs a fresh download and a second Gatekeeper visit | The owner asked for Sparkle |

## Consequences

- **Gatekeeper.** `spctl -a -vv` answers `rejected` with `origin=Apple Development: …`. The first open goes through System Settings › Privacy & Security › Open Anyway; later Sparkle updates do not ask again.
- **Privacy.** The certificate's common name, `Apple Development: <the owner's Apple ID address> (<certificate id>)`, is visible to anyone who runs `codesign -dv` on a download, and the first release publishes it for good. A Developer ID certificate names the team instead. The owner accepted this on 2026-11-25 (decision 1).
- **Trust.** The signature and the sum are served from, or documented in, the `todz.app` zone; someone who controls that zone or the Cloudflare account can replace the binary, the page and the key together. The fingerprint on the owner's GitHub account is the one anchor outside it.
- **Certificate expiry.** An Apple Development certificate lasts one year. A renewed certificate keeps the team and Sparkle keeps installing, because the EdDSA signature stays valid; a build signed after expiry fails the script's checks.
- **Moving to Developer ID.** Sparkle accepts a change of code signing identity when the EdDSA signature verifies, so installed copies update into the notarized build; the EdDSA key must never change.
- **One deploying Mac.** The release folder exists only on the Mac that built the releases; a deploy from anywhere else is refused by the staging until that folder is restored. Losing it means rebuilding it from production (the runbook's "Rebuild the release folder from production"): the served versions' three files and the appcast, each passing its sum and its signature, then `released`.
- **Every host.** Assets answer on `api.todz.app` and `www.todz.app` as on `todz.app`; the landing and the appcast name only `todz.app`.
- **Lost keys.** Losing Sparkle's key strands installed copies on their version: they need a fresh download. Losing the release key means a new allowed-signers line, announced on the docs page. The runbook keeps an exported, encrypted backup with the owner.
- **Cost.** Static asset requests are not billed as Worker invocations; the two DMGs add about 10 MB to each deploy's upload, and unchanged files are not uploaded again.

## Evidence

The spike of 2026-11-25, on this Mac only, scripts in the scratchpad, nothing committed:

- `codesign -dv --verbose=4 /Applications/Todz.app` (the current Release build): `Authority=Apple Development: … (7N2H5833HE)`, `TeamIdentifier=XFWR794VS8`, `flags=0x0(none)` (no hardened runtime, because `project.yml` sets `ENABLE_HARDENED_RUNTIME: NO`), entitlements include `com.apple.security.get-task-allow`; no `embedded.provisionprofile` in `Contents/`.
- A copy re-signed with `codesign --force --options runtime --sign "Apple Development"` and the entitlements without `get-task-allow`: `flags=0x10000(runtime)`, `TeamIdentifier=XFWR794VS8`, `valid on disk`, `satisfies its Designated Requirement`, no `get-task-allow`. The private key signed without a prompt.
- `spctl -a -vv` on that copy, with and without a quarantine attribute, and on its signed DMG: `rejected`, `origin=Apple Development: …`. The DMG: 4,670,897 bytes.
- Launching on a Mac outside this one was not observed; that check is the owner's (decision 1).
- `which minisign cosign signify`: not found. `/usr/bin/openssl version`: `LibreSSL 3.3.6`; its `pkeyutl -verify -rawin` → `unknown option '-rawin'`.
- `ssh-keygen -Y sign -n file` then `-Y verify`: `Good "file" signature for release@todz.app with ED25519 key`; one byte appended → `Signature verification failed: incorrect signature`, exit 255. The same with the key loaded by `ssh-add -` from a base64 string into an agent on a private socket: verified, and no private key file in the work folder afterwards.
- `scripts/todz-cloudflare.sh pnpm exec wrangler r2 bucket list`: `Authentication error [code: 10000]`: the token has no R2 permission, and the owner's session declined adding one account-wide. That is why decision 5 serves the files as assets.
- `apps/api/public` today: 2.1 MB with one `_headers` file (the three security headers on `/*`, a CSP on `/icon.svg`), which the staging keeps first.
- `gh api repos/sparkle-project/Sparkle/releases/latest`: `2.10.1`, published 2026-10-25; `git/ref/tags/2.10.1` → commit `ab7d71291238df6e0492143b120c9b696a35f603`. At that tag, `Sparkle/SUConstants.m` defines `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction`; `sign_update/main.swift` signs "update feed (xml)" files by embedding the signature; `SPUStandardUserDriverDelegate.h` declares `supportsGentleScheduledUpdateReminders` and `standardUserDriverShouldHandleShowingScheduledUpdate:andInImmediateFocus:`.
- Still to record, by the build: whether `_headers` applies to a `_redirects` `302`, whether it can set `Content-Type` on an asset, and whether `wrangler deploy --assets` keeps `assets.run_worker_first` (plan step 4).
