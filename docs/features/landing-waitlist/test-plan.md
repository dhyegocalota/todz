## Adversarial review

- [x] Claim 1: nothing is stored or mailed without a solved challenge and room under every limit — attack: replay a token, skip the field, flood one address, flood from many keys; result: HOLDS where reachable. No token, a wrong token, an empty token, JSON, multipart, chunked, 5 KB and a malformed address stored no row and sent no mail. On a public https host the dummy token is refused (429), D1 stayed at 0 rows. 8 parallel posts of one address made one row and one mail. Not reachable locally: a real token replay (siteverify with the dummy secret always passes) and a flood over the real limits (a local host skips them, and on the public host the dummy token fails first, so a 429 from a limit and from the token look the same); the unit rows over each limiter carry that part
- [x] Claim 2: the answer never tells whether an address is known — attack: compare bodies, headers and timings for a new and a known address; result: HOLDS. New and known `fresh1@example.com`: `cmp` found the two bodies byte-identical, headers equal apart from `Date`. 8 new/known pairs timed 2.6 to 5.4 ms with no pattern (the mail runs in `waitUntil`). The only lever is a rate limit a caller could exhaust, which treats new and known alike
- [x] Claim 3: the address never reaches a log — attack: read the Worker's console during every failure path; result: HOLDS for the Worker's own lines. After the CRLF, script, 5 KB, JSON, multipart, chunked, no-token, wrong-token and 256-character posts the wrangler log held no line with those inputs and no error; the public-host log held no address (`grep -c example.com` printed 0). The only line carrying an address is the console sender's mail (`{"to":...}`), which is the dev sender's purpose and is refused on a public host. The sender-throws path is proven by the unit "logs nothing" row, not run live
