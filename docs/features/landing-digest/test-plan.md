## Edge cases found during execution

- [x] R7, how to stop the cron. From `apps/api/node_modules/wrangler` (4.167.0, `wrangler-dist/cli.js`, read only; no deploy possible here): the schedule is its own resource, set on every deploy by `PUT /accounts/<account>/workers/scripts/todz-api/schedules` (line 60754, `if (crons) deployments.push(fetchResult(... "/schedules", { method: "PUT", body: crons.map(...) }))`), read by `GET .../schedules` (60971). `wrangler rollback` is `versionsRollbackCommand` (registered at 213684, defined at 208891): it only POSTs `/workers/scripts/<name>/deployments` through `createDeployment` (62079) with the chosen version at 100 percent, and its own warning says it replaces "the active deployment across all your deployed triggers" and rolls back no bound resource; it never touches `/schedules`. So a rollback keeps the cron, and the older version, if it predates `scheduled`, fails each fire. `"crons": []` removes it: the guard is `if (crons)` and an empty array is truthy, so a deploy with `triggers.crons = []` PUTs `[]` (the dry-run line 60652 prints `schedule: remove all` for `crons.length === 0`), while omitting `triggers` leaves `crons` undefined and the schedule alone. `resolveCronTriggers` (78878) keeps `[]` (`args.triggers ?? config.triggers?.crons`). The runbook Rollback line (deploy-the-api.md: rollback keeps `0 11 * * *`; stop with `"triggers": { "crons": [] }` and deploy) is therefore true. Not proven against Cloudflare itself: the API response to the empty PUT and the dashboard state were not read (no credentials, no deploy)
