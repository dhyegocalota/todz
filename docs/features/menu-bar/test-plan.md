## Edge cases found during execution

- [ ] FAILED: one click does not always reopen the popover after Open todz or ⌘0 closed it. Repro: main window open, popover open with the field focused; click `Open todz` (or ⌘0 into the popover); about 0.7 s later one System Events click on the status item. Expected: the popover opens with the field focused. Observed: in 33 such closes, 4 times the click opened nothing (no layer-101 window) and 2 times the popover opened without the field focused; Escape, status-item and row-click closes failed 0 of 32. Evidence: `cycles-window-open.log` (round 10: `open-todz: field not focused`, `command-zero: one click did not reopen`), `cycles-open-todz.log` (rounds 2 and 7: `one click did not reopen`, round 5: `field not focused`). Both closes activate the main window while closing the panel; the panel's key state or the status button's toggle appears to race that activation. Needs a regression check from the developer (hypothesis 1 of the briefing)
- [ ] FAILED (owner call): an add from the popover changes the main window's selection. Repro: main window on Inbox or Today with nothing (or a task) selected; add `Ship the menu bar` from the popover. Observed: once the server confirms, the main window selects the new task and its inspector loads it (`GET …/tasks/1/history`, again `…/34/history` and `…/35/history` for the offline adds; `07-main-after-add.png`). Cause: mac-sync's select-on-confirm rule (`AppModel+Outbox.swift` `select`) fires for any add while the selection is unmoved and the project is shown. `design.md` O2 makes the row click "the one place where the popover changes the main window's view". Expected per design: the window's selection unchanged by a popover add
- [ ] MINOR: the empty-Today body `Tasks due today or earlier show up here.` renders in the primary colour in the popover (`05-empty-today.png`); `design.md` § 3 lists the empty body as `.secondary`
- [x] The main window reopens on every relaunch, even after it was closed and the app waited 3 s before the pkill (two runs); the developer's risk (a) note saw no window restored. The box allows either; the popover was ready each time with one `PATCH /owner`
- [x] ⌘R in the popover pulls only the projects the app knows: a project created through the owner API on another client appears only after a relaunch. Same as the main window's Refresh (mac-sync), not introduced here
- [x] With the popover key, a background click on the main window's sidebar closed the popover (the panel resigned key), the closest background input gets to "click elsewhere closes"; while it was not key, clicks in the main window left it open
- [x] Open todz and a row click do not make todz frontmost under background input (Slack stayed frontmost both times); the main window is on screen behind

## Adversarial review

## Coverage honesty

- The app target has no test target: the popover's views are proven only by the walk.
- Key equivalents are pressed through Orca's background hotkey into the popover window; whether they reach a `MenuBarExtra` panel that is not key is a hypothesis the walk checks.
- Background input cannot make a window key or frontmost, and cannot click outside the popover to close it: "click elsewhere closes", "the main window is frontmost" and anything that needs the main window key are recorded as what the CoreGraphics window list shows, or BLOCKED with the reason.
- The switcher's menu is an `NSMenu` pop-up; opening it in the background is tried with System Events AXPress, else BLOCKED.
