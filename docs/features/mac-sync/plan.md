# Plan: Mac sync

**Spec:** spec.md
**Tier:** 🔴
**Seam:** `apps/macos/TodzKit` (new cache, outbox, overlay, feed cursor and socket units; `AppModel` routes task writes through the outbox and gains the cache and the watchers) and `apps/macos/Todz` (the sync status item, pending rows, the refused notice, the sign-out confirmation, injection of the store and the sockets). Nothing outside `apps/macos` changes but this folder's docs.
**Assumptions (decided, owner can override):**
- ADRs 0027 to 0029 and `design.md` § 7 are the loop's calls, listed in the loop's questions. No third-party Swift dependency.
- Swift 6 language mode, strict concurrency, Swift Testing, `swift test` from `apps/macos/TodzKit`, as in the shell's plan; its convention bullets hold here word for word (no comments but `// NB ADR NNNN:`, no `??` default, flat `guard`s, enums over literals, constants at the top, labels, array methods, no acronyms).
- Every cached shape is encoded with `OwnerCoding.encoder()` and decoded with `OwnerCoding.decoder()`, so a cache file looks like an owner API answer (snake_case, dates as epoch milliseconds).
- Tests never touch the real container: `FileSyncStore` takes its folder; tests pass a temporary folder.
- The backoff waits through an injected `pause: @Sendable (Duration) async throws -> Void`. Production passes `Task.sleep(for:)`; tests pass a pause that records the durations and suspends until the test releases it. No test waits on the clock.
- Files are written with the Write and Edit tools: `guard-secrets.sh` blocks code heredocs and any shell line with an expansion.
- Red-first as in the shell: each red commit holds the failing test alone, plus stubs that `fatalError("<name> is not implemented")` and the types the test compiles against; its body records the failure the red run printed. A test that is green when it lands is a `pin`.

## Sequencing

G1a and G1b run in parallel, one worktree each, branched from `feat/mac-sync`; neither touches the other's files. G1b may change the single `TaskViews(…)` call in `AppModel.swift` and the `ProjectPull.loaded` match in `AppModel+Workspaces.swift` so the package compiles; no other G2 line. The lead merges G1a, then G1b (merge, never rebase), runs `swift test`, and hands G2 to `developer-model` on the merged branch. G3 starts after G2 is merged, because the views read `AppModel`'s new state.

## Steps

Author this list with every box empty. A sub-agent ticks its own line. A wrong step is struck through with the reason, not deleted.

### G1a cache

- [ ] **Step 1:** red then green: `OwnerCoding.encoder()` writes dates as epoch milliseconds (an `Int64`) and keys in snake_case; `Owner`, `Project`, `Workspace`, `ChangeActor`, `TaskRecord` and the enums become `Codable`, each `encode(to:)` mirroring its `init(from:)` (`ChangeActor` writes `kind` and, for an agent, `client_name`; `Project` and `Workspace` write `id`). `OwnerCodingTests`: every fixture of `OwnerFixtures` decoded, encoded and decoded again equals the first decoding; an encoded task holds `"created_at":1764000000000` and `"due_date":"2026-11-24"`; a task with `notes: nil` encodes `notes` as absent or `null` and decodes back to `nil`.
- [ ] **Step 2:** refactor, pin: the `0600` draft-then-`rename` write and the backup exclusion of `FileSessionVault` move to `PrivateFile.write(_ data: Data, to file: URL)` (it creates the folder with mode `0700`); `FileSessionVaultTests` stay green unchanged. `SessionVaultError.unwritable` still names a vault failure: `PrivateFile` throws its own `PrivateFileError.unwritable`, mapped by the vault.
- [ ] **Step 3:** red then green: `SyncStore` protocol (`readOwner`, `writeOwner`, `readProject(identifier:)`, `writeProject`, `eraseProject(identifier:)`, `readOutbox`, `writeOutbox`, `erase`), `OwnerCache { ownerIdentifier, workspaces, activeWorkspaceIdentifier: String? }`, `ProjectCache { projectIdentifier, cursor, tasks }`, `SyncStoreError { unreadable, unwritable }`, and `FileSyncStore(folder:)` over the `Cache` folder. The outbox is read and written as `Data` encoded by the caller's type, so G1a does not depend on G1b: `readOutbox() throws -> Data?`, `writeOutbox(_ data: Data) throws`. `FileSyncStoreTests` in a temporary folder: nothing written → every read answers `nil`; each write then read answers the same value; files are `0600` and the folder `0700`; a project id is used only as a file name after it matches `^[A-Za-z0-9-]{1,64}$` (else `SyncStoreError.unwritable` on write and `nil` on read, so a hostile id never escapes the folder); a file holding `{` → `SyncStoreError.unreadable`; `erase` removes the folder and runs twice without error; `isExcludedFromBackup` is true on every written file; writing a `ProjectCache` of 1 000 tasks takes less than 16 ms (median of 5 runs).

### G1b outbox and pull

- [ ] **Step 4:** red then green: `TaskDraft`, `TaskPatch`, `TaskPlacement`, `TaskKey` become `Codable` (`TaskPatch` decodes the one key present back to its case; `notes: null` and `due_date: null` decode to `.notes(nil)` and `.dueDate(nil)`, so absence of the value is never confused with absence of the key). `PendingChange`: `add(projectIdentifier:draft:)`, `field(TaskKey, TaskPatch)`, `state(TaskKey, TaskState)`, `Codable` with a `kind` discriminator (`PendingChangeKind` enum), plus `projectIdentifier`, `taskKey: TaskKey?` and `writeField: TaskWriteField?`. `PendingChangeTests`: each case round-trips through `OwnerCoding`; an unknown `kind` fails decoding.
- [ ] **Step 5:** red then green: `Outbox` (value type, `Codable` as `{ changes: [{ change, attempts }] }`): `appending(_:)` replaces a waiting change of the same task and field in place and resets its attempts, except `.field(_, .placement)`, which is always appended; complete after reopen (or the reverse) on one task leaves one `.state` change; `head`, `removingHead()`, `countingAttemptOnHead()` (returns the outbox and whether the head reached `OUTBOX_ATTEMPT_LIMIT` = 3), `droppingChanges(projectIdentifier:)`, `count`, `pendingAdds` (the adds as `PendingTask { projectIdentifier, idempotencyKey, title, dueDate }`). The head is never replaced while it is being sent: `appending` takes `isHeadSent:` and, when true, a change for the head's task and field is appended instead. `OutboxTests`: two title edits of T-1 → one change holding the second title, at the first one's position; two moves of T-1 → two changes in order; complete then reopen → one `.state(open)`; three attempts on the head → `isAtLimit` true; an edit of the sent head's field → appended after it; `droppingChanges` keeps the other projects' changes in order.
- [ ] **Step 6:** red then green: `TaskBoard.applying(_ outbox: Outbox) -> TaskBoard`: a waiting title, notes or due date replaces the held task's field; a waiting `.state(done)` sets `state` done and `completedAt` to the change's own time (passed in as `now`), `.state(open)` clears it; a task the board does not hold ignores its changes; for each project with waiting moves, the moves are applied in outbox order to that project's open tasks in their manual order (`first` puts it at the top; `after n` right after task n; an anchor the list does not hold leaves the task where it is), then the project's open tasks get display order keys `"0000"`, `"0001"`, … in the resulting order; done tasks keep their keys. `TaskBoard.cursor(projectIdentifier:)` and `setting(cursor:projectIdentifier:)` hold each project's cursor. `TaskBoardOverlayTests`: each field alone; a completed overlay moves the task from Inbox to Done in `TaskViews`; the sequence from the brainstorm (open T-1 X, T-2 Y, T-3 A, T-4 B; moves A after X, B after A, A first) gives A, X, B, Y; moving T-2 after a task that is not in the list leaves the order unchanged.
- [ ] **Step 7:** red then green: `TaskViews(projects:board:pendingTasks:day:timeZone:)` keeps every existing list unchanged (so the app target still compiles) and gains `pendingTasks(for item: SidebarItem) -> [PendingTask]`: the Inbox and a project → that project's pending adds in the order they were added; Today → pending adds of the workspace due today or earlier; Upcoming → due later, by due date; Done → none. The list shows them after its open rows; Upcoming's view groups them by `dueDate` into its days. A pending task of a project outside the workspace is never returned. `TaskViewsTests` gain: a pending add in the Inbox is returned for Inbox only; one due today for Today; one due tomorrow for Upcoming; one without a due date not for Today; none for Done. The one `TaskViews(…)` call in `AppModel.swift` passes `pendingTasks: []` until G2 wires the outbox.
- [ ] **Step 8:** red then green: `ProjectFeed.pull(session:projectIdentifier:cursor:) -> ProjectChanges { tasks, cursor, isFromStart }`: from cursor 7 the first request carries `cursor=7`; pages are followed until `has_more` is false and the last page's cursor is returned; `cursorAhead` → one pull from 0 with `isFromStart` true; a second `cursorAhead` throws. `ProjectPull.loaded` carries `ProjectChanges`. `ProjectFeedTests` updated and extended.
- [ ] **Step 9:** red then green: `ReconnectDelay.after(attempt:) -> Duration`: attempts 1…6 → 1, 2, 4, 8, 16, 30 seconds, every later attempt → 30 (`ReconnectDelayTests`, attempts 0 and negative are a `precondition`).
- [ ] **Step 10:** pin then live: `ChangeSignals` protocol `watch(session:projectIdentifier:) -> AsyncThrowingStream<ChangeSignalEvent, any Error>` with `ChangeSignalEvent { opened, changed }`; `SocketChangeSignals(baseURL:)` turns `http`/`https` into `ws`/`wss`, opens `URLSessionWebSocketTask` with `Authorization: Bearer <session>` on `/owner/projects/<id>/socket`, yields `opened` on the first successful `receive` or when the task's `response` is a 101, `changed` for each `changed` text, and finishes with `OwnerAPIError.unauthorized` (response 401), `.notFound` (404) or `.unreachable` (anything else); cancelling the stream cancels the task. A unit test checks the URL and header the request is built with (`socketRequest(session:projectIdentifier:)`, internal). `LiveOwnerAPITests` gains: with `TODZ_LIVE_API_URL`, a watch on a new Inbox yields `opened`, then `changed` after an add through `OwnerAPI`; a watch with a wrong session finishes with `unauthorized`.

### G2 model

- [ ] **Step 11:** red then green, the harness: `InMemorySyncStore` (records every call, can fail any of them with a set error, starts from given contents), `FakeChangeSignals` (one controllable stream per `(session, projectIdentifier)`, records opens and cancellations), `HeldPause` (records durations, suspends until released), `AppModel(service:vault:store:signals:timeZone:now:pause:makeIdempotencyKey:)`. A cached launch: with a session and an `OwnerCache` of one workspace and two projects with tasks, `launch()` answers `phase == .ready` and the cached rows in `taskViews` while `updateOwner` is still held; then `updateOwner`, `listWorkspaces`, and one `readChanges` per project with the stored cursor; the store receives `writeProject` with the new cursor. A launch without a cache is unchanged (the shell's tests stay green).
- [ ] **Step 12:** red then green, owner and privacy: sign-in answers an owner equal to `OwnerCache.ownerIdentifier` → the cache stays and the outbox is sent; a different owner → `store.erase()` is the first store call, before any write; `signOut()` → `store.erase()` then `vault.erase()`; `waitingChangeCount` is the outbox's count; a 401 → `phase == .signedOut(notice: .sessionEnded)`, the store is not erased, every watch is cancelled, and `waitingChangeCount` survives for the sign-in screen's line.
- [ ] **Step 13:** red then green, the outbox: `complete`, `reopen`, `updateTitle`, `updateNotes`, `updateDueDate`, `move` and `addTask` append to the outbox and call `store.writeOutbox` before any service call; `taskViews` shows the change while the service call is held; an answer removes the head, the board takes the server's record, the outbox is written again; the next change is sent only after the first answers (one call at a time, in order); `unreachable` keeps the change, `syncStatus == .offline(waiting: n)`, and nothing more is sent until a watch yields `opened` or `refresh()` runs; `ruleViolated`, `taskNotFound`, `notFound` or `invalidRequest` drops the change, pulls its project from cursor 0, and raises `.changesRefused(count:)` once for that flush (two refusals in one flush → one banner with count 2); `unexpected` three times on one change drops it as refused; a 401 mid-flush stops and keeps the rest. An add answered by the server becomes a normal task and is selected when the selection did not move since the add; `replayed: true` is treated the same. `ruleIssues` and the inline field errors of the shell still show for checks made before sending (`TextCheck`).
- [ ] **Step 14:** red then green, pulls and sockets: activating a workspace opens one watch per project and cancels the previous workspace's; `changed` pulls that project from its cursor; a `changed` during a pull of that project runs exactly one more pull after it (three `changed` during one pull → two pulls in all); `opened` sends the outbox, then pulls that project; a stream that finishes with `unreachable` reopens after `pause(ReconnectDelay.after(attempt:))`, the attempt growing until a successful `opened` resets it; `unauthorized` ends the session; `notFound` reloads the workspaces; `cursor_ahead` resets the project's tasks before merging (`isFromStart`); after every pull the store gets `writeProject` and after `listWorkspaces` it gets `writeOwner`.
- [ ] **Step 15:** red then green, the cache failing: a `writeProject`, `writeOwner` or `writeOutbox` that throws raises `.cacheNotSaved` once per launch and the model goes on; `readProject` throwing `unreadable` → `eraseProject` and a pull from 0; `readOwner` throwing → `erase` and the shell's loading path; `readOutbox` throwing → an empty outbox written and `.waitingChangesLost` raised once.
- [ ] **Step 16:** red then green, the status: `syncStatus` is `.online` when the last send or pull reached the server and `.offline(waiting:)` when the last one was `unreachable` or `unexpected`; it returns to `.online` on the next answer; a pull failure with cached rows raises no banner, and the shell's banners stay for projects with nothing cached (`design.md` § 1.6).

## Failure modes

| Step | What breaks | How I notice (the concrete signal) | How I back out |
|------|-------------|------------------------------------|----------------|
| 1 | an encoded date round-trips with sub-millisecond drift, so `TaskBoard`'s `updatedAt` guard rejects a cached copy | the round-trip test's `==` fails on `updated_at` | encode `Int64((date.timeIntervalSince1970 * 1000).rounded())`, decode as today |
| 3 | a project id from the server escapes the folder (`../`) | the hostile-id test writes outside the temporary folder | ids pass the pattern before use as a file name |
| 3 | tests write the real container | a `Cache` folder appears under `~/Library/Containers/dev.todz.Todz` after `swift test` | the store takes its folder; tests pass a temporary one |
| 5 | coalescing a move in place reorders differently from the screen | the brainstorm sequence test gives A, B, X, Y on the server and A, X, B, Y on screen | moves are always appended |
| 6 | display order keys leak into an `after` anchor or a write | a `PATCH` carries `"0003"` | keys never leave `TaskBoard.applying`; placements carry numbers |
| 10 | `URLSessionWebSocketTask` never reports `opened` on a quiet socket | the live test waits for `opened` forever | `opened` also on `response` status 101 after `resume()`, checked by the live test |
| 10 | a socket's failed upgrade has no `response` | the stream finishes `unreachable` for a 401 | the live test with a wrong session pins `unauthorized` |
| 13 | two sends run at once and the server applies them out of order | the fake records two calls before the first answers | one `sendOutbox` task at a time, guarded by a flag |
| 13 | a refused head is retried forever | the fake records the same call more than three times | attempts per head, dropped at the limit |
| 14 | a workspace switch leaves old sockets open | `FakeChangeSignals` records an open stream for a project of the old workspace | `activate` cancels every watch task before starting the new ones |
| 14 | a `changed` storm runs a pull per message | the fake records more pulls than the coalescing rule allows | one pull in flight per project, one queued |
| 15 | an unreadable outbox signs the owner out or crashes | the launch test does not reach `ready` | the outbox read is its own branch |
| 17 | `Task.sleep` trips `warn-conventions.sh` | the hook warns on `sleep` | expected: it is the production pause, not a test wait; noted in the briefing |
| 18 | the linger leaves a completed task in the list after a pull confirms it | the walk shows a done row in Inbox after a second | the linger is a view state keyed by task and cleared by its timer only |

**Steps with no backout:** none; nothing is deployed and nothing outside `apps/macos` depends on it. A cache written by a build of this branch is ignored by the shell.
